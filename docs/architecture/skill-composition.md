# Skill Composition

This product provides portable semantic capabilities, not an agent loop or orchestration runtime. Generic workflows work independently of a particular agent host, and no Skill requires an architecture checkout.

## Product Contract

- Directly matched Skills do not require a router. `skills-routing` is the single optional selection entry, with independent references for Skill selection, tools, implementation languages, verification methods, simplification and session recovery. Read the relevant branch rather than loading all methods or rerouting an already settled task.
- The active agent chooses one primary response owner and useful overlays; `output-styles` owns presentation and response-composition guidance. User formats, repository artifact conventions and actual consumer schemas apply where required; otherwise the primary method organizes the deliverable. Supporting Skills and references contribute relevant evidence without imposing their own templates or expanding the investigation to populate fields. Several requested artifacts receive one synthesized final response. Installed routing guidance declares real semantic dependencies, not fixed phases or executable transitions.
- Review is conditional on explicit intent, applicable policy or evidence-backed risk. Standalone review needs its bounded target, not reconstructed lifecycle artifacts. Evaluators are read-only; the calling agent judges findings and authorizes repair.
- Skills preserve task authority and protected behavior. They do not grant publication, deployment, commit, push, installation or destructive mutation. Current project records may have an explicitly declared external owner; summaries are recall, not new authority.
- Bounded implementation and verification labor may be delegated when the host permits it. A writable managed child owns one repository; the main agent integrates cross-repository work and keeps acceptance. Generic workflows do not depend on a specific host tool, scheduler, route or persistent ledger. A named tool Skill may require its named tool and companion guidance without introducing a product runtime or provider adapter.
- An implementation follows the authorized main goal through verified delivery. Secondary discretion must already be authorized; a failed check or unavailable helper is not permission to lower acceptance. Ordinary diagnosis and in-scope repair do not require restarting design.
- `development-standards` supplies the necessity and maintenance baseline from design through planning, implementation and review. The agent considers simplification before adding mechanisms; it does not create a separate audit stage. The simplification method under `skills-routing` supports requested assessments across code, tests and documentation, including bounded ablation when useful, and routes authorized application to the existing implementation workflow.
- Documentation follows repository conventions and the shared expression baseline while it is drafted and revised. `organize-docs` repairs observed drift within the authorized scope rather than imposing a routine restyling pass. Required ownership, link and placement checks remain distinct from prose preferences.
- Code and execution establish implemented behavior; documents and diagrams convey intent and explanation and are synchronized after changes. Their contents are not test interfaces. Ordinary local evidence does not require hashes, immutable receipts or revision ceremonies; actual functional and trust requirements retain their own integrity mechanisms.
- Product validation covers the authored inventory, discovery, reference closure and ordinary code quality. Passing static checks does not establish live-model effectiveness or reduced cost.

## Maintained Methods

The directories under `skills/` own the detailed methods, exceptions and recovery semantics and are copied explicitly for installation. Main instructions retain the complete task path and the conditions for reading detailed references; moving detail into a reference does not change whether the Skill activates. See [design-change](../../skills/design-change/SKILL.md), [plan-change](../../skills/plan-change/SKILL.md), [implement-change](../../skills/implement-change/SKILL.md), [review-change](../../skills/review-change/SKILL.md), [sync-truth](../../skills/sync-truth/SKILL.md) and [close-change](../../skills/close-change/SKILL.md). Generated semantic diagrams remain local under `diagrams/` and `generated/`.

[herdr-implement](../../skills/herdr-implement/SKILL.md) composes `implement-change` and `review-implementation` for an explicitly requested main-to-main handoff through Herdr. The implementing main owns implementation, verification and finding adjudication; the current main owns the outer review loop and final response. Each main controls its own native subagents. This handoff uses the separately installed external `herdr` Skill; it neither vendors that Skill into the inventory nor manages the mains' internal delegation.

The shared explanation, decision rationale and cross-product ownership view are maintained at `$AGENT_ARCHITECTURE_DIR/docs/architecture/skill-composition.md` and `repository-boundaries.md`. These references are maintainer context, never runtime imports. Install and maintenance boundaries remain in [install-surface](install-surface.md) and [maintenance-contract](maintenance-contract.md).
