# Maintenance Contract

`skills/<public-id>/` is the single authored and installable tree. `contracts/skills.toml` owns public IDs, activation mode, default role, mutation guards, and real semantic dependencies; directory paths follow the public IDs. Provider metadata, including effective activation policy, is authored directly alongside each Skill. Each Skill's body owns its own admission boundary, and its description summarizes that boundary for selection with only the most confusable exclusions. The installed routing contract owns the scope contract between neighboring Skills: clusters, each cluster's distinguishing question, and handoffs that name a receiving Skill, a method reference, or no Skill. `routing.md` owns session selection rules; neither has phase, mode, or gate authority.

Activation modes are host-neutral. A `native` Skill may be selected for any matching request; a `conditional` Skill overlays a primary owner while its boundary is active; a `baseline` Skill always participates in composition; a `composition` Skill loads only through a named composer; an `explicit` Skill loads only when the user names it or explicitly asks for its workflow. Codex projects the mode through `policy.allow_implicit_invocation` in `agents/openai.yaml`, which is true for native, conditional, and baseline Skills and is compared with the inventory. Hosts that list every installed description carry explicit and overlay boundaries through description markers and body guards, which semantic review checks.

`tests/fixtures/selection-probes.toml` holds paired selection probes: a request, its expected primary owner, optional overlays, and a counterexample that expects a different selection. The probes are maintenance material for discovery-layer audits and requested behavioral comparisons. They are not installed, and checks validate only their identifiers and targets, never model behavior.

Renaming or retiring a public ID updates the inventory, scope contract, probes, and Skill references in the same change. Installed copies and host global entries that name the ID, such as the `skills-routing` pointer in user-global instructions, are consumer state; report the needed removal or entry update instead of editing them.

Authored `.puml` sources and the Bash `scripts/render-diagrams.sh` entrypoint maintain architecture views through real PlantUML rendering. Static checks inspect the authored tree directly for parseability, inventory, discovery metadata, reference closure, documentation, lint, types, and tests. There is no second tracked Skill tree, generated inventory index, or source/distribution parity gate. Checks do not validate workflow artifacts, enforce a lifecycle, or execute agent behavior.

Global installed content changes only through explicit installation or update. Source editing, Git operations, diagram generation, and maintenance checks do not refresh it. See [install-surface](install-surface.md) for local-path refresh, remote updates, and removal; installation state remains consumer-owned.

Instruction changes use bounded semantic inspection and appropriate prose, link, and distribution checks after related edits. Executable changes use their focused checks; broad product checks and diagram generation apply when the affected surface or delivery requirement needs them. The main agent coordinates integration and full-suite evidence, retaining applicable worker results and rerunning only invalidated evidence after repair. Goal-and-risk counterexamples under `testing-strategy` support optional controlled comparisons, not mandatory live-model trials. Passing maintenance checks does not establish fewer interruptions, lower cost, or safer agent behavior.

`skill-miner` also reads native Pi v3 session JSONL, with explicit recorded-branch selection, incomplete/fork evidence limitations, separate stop/model observations, and categorical rather than raw Pi text samples. These are candidate mining signals, not automatic judgments of task success or premature stopping. Its synthetic CLI regression suite lives under `skills/skill-miner/tests/`; run it explicitly because root pytest discovery does not include nested Skill tests. Parsing needs no Pi runtime, user histories, credentials, or model experiment.
