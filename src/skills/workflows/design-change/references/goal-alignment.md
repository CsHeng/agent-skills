# Goal Alignment

Use this reference only when a concrete goal-means mismatch, acceptance ambiguity, material tradeoff, or authority gap actually blocks progress. Do not start a default interview, and do not send an already bounded implementation through a full design workflow to obtain a `no-design` credential.

## Goals, Means, And Hard Constraints

Separate the outcome the user wants, the hard constraints that already bind the work, and the implementation means that remain replaceable. A named tool or approach is not proof that the goal is unclear. Do not overwrite an approved decision with a preferred alternative.

Main goals, their necessary conditions, user-fixed technical choices, and applicable inviolable boundaries must be met. Authorized best-effort secondary work may be substituted, degraded, or omitted during implementation when evidence supports that adaptation, while the main goal continues. Record that discretion and its limits; do not pre-enumerate every feature that might fail, and do not require design investigation to implementation depth.

Discretion comes from the current request, an approved design, or an applicable project convention. Do not self-grant it after the fact to obtain a pass. An explicitly required deliverable cannot be relabeled secondary. A capability named secondary still cannot be dropped if it is a necessary dependency of the main goal, then reported as main-goal completion.

When the user specifies a library or equivalent technical choice to achieve a goal, that choice binds. Glue, helpers, and local algorithms stay with the executor. Without authorized substitution, do not replace the specified library for preference, and do not ask the user to design each glue function.

## Investigate Facts; Ask Only The Owner

Discoverable facts in authorized code, docs, config, and tools belong to targeted agent investigation. Keep that investigation proportional to the current decision; do not escalate it into a repository-wide audit. Local implementation choices that are already in an executor's scope stay with that executor under project conventions and the confirmed constraints. Changing models or reviewers does not send those local choices back to the user.

Bindings, digests, receipts, and other execution products the agent can generate are not human prerequisites. Ordinary bugs, a single failure, or unknown feasibility do not by themselves prove a goal unsupported; gather enough investigation or experiment to explain a tradeoff, without exhausting every alternative.

Ask a person only when the answer would change the goal, external behavior, material state, acceptance, or authority, and send that question to the owner who can actually decide it. Before asking, say what different reasonable answers would change, whether the decision is already delegated, whether it must be made now, and whether cheaper runtime evidence can wait. Questions that need a prototype or experiment are not settled by more questionnaires.

Each question carries the necessary evidence, a recommended judgment, and the material consequence of that recommendation. Do not fix a maximum question count, and do not walk unused design branches.

## Finish Clarification And Resume

End clarification once the next authorized step can proceed reliably and remaining unknowns can be investigated, implemented, verified, or reasonably deferred. After the user answers the blocking question, resume the original authorized task; do not end on confirmation, a restated plan, or a promise to continue. Local technical difficulty belongs to diagnosis or in-discretion tradeoff, not an automatic new design or plan.

Reopen a settled decision only when new evidence materially changes that confirmed boundary. Changing models, reviewers, or implementation tactics is not a reason to reopen it.

If an adaptation would change the main goal, or would make a later production action's commitments, risk, goals, or permissions exceed the approved boundary, pause that affected action and obtain a narrow authorization before the impact. Independent, safe, authorized work continues. Do not disclose a newly material production risk only after going live. Credentials, tool capability, and review success do not create operational permission.

Record the material decisions and necessary reasons in the existing design, plan, or requirement source of truth. Distinguish user decisions, unknown facts, implementation products to generate, technical verification, implementation assumptions, recommendations, and user approvals. Do not assign permanent question IDs or create a separate requirements ledger.

A single in-flight clarification belongs to the original task: resolve that one decision and resume the original authorized work. Ordinary bounded clarification does not enable stress-test mode, does not mint frontier or `Q*` identifiers, and does not start this Skill's full design workflow.
