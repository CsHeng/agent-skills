# Goal Alignment

Use this reference only when a concrete goal-means mismatch, acceptance ambiguity, material tradeoff, or authority gap actually blocks progress. Do not start a default interview, and do not send an already bounded implementation through a full design workflow to obtain a `no-design` credential.

## Goals, Means, And Hard Constraints

Separate the outcome the user wants, the hard constraints that already bind the work, and the implementation means that remain replaceable. A named tool or approach is not proof that the goal is unclear. Do not overwrite an approved decision with a preferred alternative.

## Investigate Facts; Ask Only The Owner

Discoverable facts in authorized code, docs, config, and tools belong to targeted agent investigation. Keep that investigation proportional to the current decision; do not escalate it into a repository-wide audit. Local implementation choices that are already in an executor's scope stay with that executor under project conventions and the confirmed constraints. Changing models or reviewers does not send those local choices back to the user.

Ask a person only when the answer would change the goal, external behavior, material state, acceptance, or authority, and send that question to the owner who can actually decide it. Before asking, say what different reasonable answers would change, whether the decision is already delegated, whether it must be made now, and whether cheaper runtime evidence can wait. Questions that need a prototype or experiment are not settled by more questionnaires.

Each question carries the necessary evidence, a recommended judgment, and the material consequence of that recommendation. Do not fix a maximum question count, and do not walk unused design branches.

## Stop When The Next Step Can Proceed

Stop once the next authorized step can proceed reliably and remaining unknowns can be investigated, implemented, verified, or reasonably deferred. Reopen a settled decision only when new evidence materially changes that confirmed boundary. Changing models, reviewers, or implementation tactics is not a reason to reopen it.

Record the material decisions and necessary reasons in the existing design, plan, or requirement source of truth. Distinguish unknown facts, implementation assumptions, recommendations, and user approvals. Do not assign permanent question IDs or create a separate requirements ledger.

A single in-flight clarification belongs to the original task: resolve that one decision and return. Ordinary bounded clarification does not enable stress-test mode, does not mint frontier or `Q*` identifiers, and does not start this Skill's full design workflow.
