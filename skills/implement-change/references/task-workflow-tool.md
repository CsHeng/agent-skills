# Task Workflow Tool

Read this reference only when the host exposes a task-level workflow tool with completion-contract support and the approved implementation obligations must be represented in it. It defines how to project those obligations through a portable host boundary rather than any private implementation: the tool's record schema, identifiers, and lifecycle mechanics belong to the host, and this reference must not assume a particular provider, extension schema, or private field. A generic todo list or task display is not such a contract, and tool availability does not grant authority or select a different lifecycle.

Host-managed identities and consistency checks remain inside the host. Do not recreate them as repository receipts, document hashes, test gates, or extra user obligations. Evidence applicability follows the changed behavior, inputs, and conditions; obey required host mechanics without making byte identity a general development goal.

## Project The Obligations

- Project the approved goal, required delivery and verification, applicable review obligations, and real dependencies. Preserve stable IDs and independently deliverable plan task boundaries; do not collapse independent owners into one umbrella task or turn display grouping and stage order into dependencies. Split outcomes that can be accepted or blocked independently, without tracking every command as a task. Overall milestone acceptance remains distinct from the outputs actually needed by each consumer. The main agent owns their meaning and applicability; the host owns record identities, revisions, execution associations, and mechanical consistency. Do not require a named Skill, provider, or extension schema on either side.
- Follow the host's scope and input-field semantics, and bind evidence to the actual inputs of the claimed outcome, not a task description or every path checked in the milestone. Preserve the plan's verification ownership when projecting checks into attempts: separate foundation, consumer, and join checks where their acceptance differs. If downstream edits repeatedly revoke an otherwise independent foundation or sibling, inspect evidence-input overlap as well as task dependencies. Repair mistaken grouping through supported operations and reverify affected outcomes; do not merely repeat the broad check, drop real inputs from its scope, weaken required compatibility evidence, or rewrite stored history to restore acceptance.

## Report Provenance And Acceptance

- Report semantic milestones and real evidence with explicit provenance. Record a slice's actual outcome when its checks or work reach a decision boundary, before switching away from finished work, blocking, handing off, or giving the final response; do not defer all progress recording to final closure. Partial or failed work may be reported without acceptance.
- Accept a locally verified task when its applicable requirements are met, while retaining any genuinely required integration or independent review. Keep acceptance a main-agent judgment: a host observation is not automatically a passing test, and a completed child apply is an integration fact, not acceptance. Use supported compound updates instead of per-tool bookkeeping; keep independent concurrent attempts distinct and start a new attempt when further work follows a finished one.
- Reconcile changed user intent before changing obligations. Ordinary conversation tasks do not automatically become required implementation gates; neither a display toggle nor a plain todo completion can satisfy or cancel the contract.

## Amend And Recover

- Use the tool's supported amendment path when the approved requirements or their execution representation change. Split an oversized task under existing authority when it hides independent progress or blockers; preserve unchanged task identities and unrelated accepted evidence, replace only mistaken representation dependencies, and verify new split outcomes rather than inheriting the aggregate's acceptance. Respect the host's replacement/update semantics so omitted unrelated tasks are not accidentally removed. Do not weaken acceptance, invent evidence, or cancel unfinished obligations merely to silence a continuation reminder.
- Before waiting or ending, inspect available work, task-local blockers, and actual unmet dependencies. A local blocker affects its corresponding task, not all owners or joins. Continue independent authorized work; unfinished classification, implementation, authorized setup or fixture preparation, verification, or review is work to perform, not an external unblock condition. A rejected dependency check calls for satisfying the predecessor or correcting the representation, not bypassing acceptance or suspending the whole task. Mechanical readiness does not grant authority or override a real user pause, host interruption, or operational inability to continue.
- Update external plan or project records only when their meaning changes, not after every task transition. A host bookkeeping failure is not business completion; preserve the real work and report the unsupported tracking state instead of inventing identifiers or repeatedly guessing protocol repairs.
