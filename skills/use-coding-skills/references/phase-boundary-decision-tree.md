# Phase-Boundary Decision Tree

Choose how to carry context from one completed coding phase into the next without turning session mechanics into another lifecycle authority.

## Entry Condition

Apply this tree only at a completed phase boundary, after one coherent analysis, design, planning, implementation, verification, or review phase has reached its owning stop state. Mid-phase, continue the current work unless a separately authorized and independently scoped delegation can proceed without losing the active reasoning thread.

Evaluate the branches in order and take the first applicable branch.

## Ordered Branches

### PB1 - Continue

Continue in the current context when the next phase needs the present conversation as a primary source and the session remains viable. This preserves decisions, rejected alternatives, and causal reasoning without converting them into a summary.

### PB2 - Discard Irrelevant Context

Start the next phase without carrying the current context when the completed phase is irrelevant to what follows and its durable results already live in repository-owned truth. Do not discard context that still owns an unresolved decision, verification state, or recovery boundary.

### PB3 - Portable Handoff

Create a portable handoff when context must travel to another harness, repository, directory, colleague, or separately resumed side task. Portability is the reason for this branch; a handoff is not the default summary mechanism inside the same active scope.

### PB4 - Policy-Permitted Delegation

Delegate a tightly scoped task only when the selected skill or approved execution policy permits delegation and the task can complete without redefining scope, authority, topology, or oracles. This reference does not authorize delegation, parallel execution, writable shared checkouts, or recursive delegation.

### PB5 - Compact Fallback

Compact the relevant context when it must remain available, continuing in the current context is no longer viable, and none of the earlier branches applies. Compact is the fallback because it replaces the primary conversation with a lossy secondary source.

## Payload Ownership

When PB3 or PB5 applies, use the `Compact Instructions` section in the owning `use-coding-skills` skill for payload priority. Do not duplicate architecture decisions, modified files, verification state, open gates, or tool-output rules here.

## Boundaries

- Express each branch semantically; the host decides how to continue, reset, hand off, delegate, or compact.
- Use observed context pressure and next-phase needs instead of a fixed context-window threshold.
- Keep lifecycle transitions with their workflow owners. This tree selects a context operation only.
