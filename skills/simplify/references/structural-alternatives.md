# Structural Alternatives

Read this for a requested reassessment of an owned architecture, replacement of a bespoke mechanism, or a refactor-versus-rewrite comparison.

Bound the inquiry to the requested responsibility. Identify the responsibility owned, observable behavior, consumers, data and compatibility obligations, the maintenance burden the user wants to reduce, and the declared maintenance horizon. Compare continuing the current implementation, local simplification, and a concrete mature alternative, checking the project's existing facilities and primary documentation before declaring an alternative inadequate; stop when the evidence supports a decision. Count migration, adapter glue, deployment and dependency ownership, licensing and platform constraints, verification, maintenance, and future extension; a larger one-time rewrite is justified when it removes durable responsibilities; assess sunk cost, popularity, and local line count in the full comparison. A new bespoke component names the specific gap, reliability constraint, or integration or performance advantage it answers, and the replacement's verification and recovery mechanisms justify their own cost against current risks.

Return the bounded responsibility, verified alternative capability and gaps, retained contracts, migration consequences, expected tradeoff, uncertainties, and whether a separate design decision is needed. No worthwhile replacement is a valid result. A replacement the user has chosen continues through `implement-change`; an unresolved requirement gets a narrow decision through `design-change`.
